# Decisions

One entry per decision: what, and why in a sentence or two. When a decision
is replaced, the old entry is marked *superseded* and points to the new one;
it is not rewritten.

| # | Decision | Why |
|---|---|---|
| 1 | Shared core in Rust; SwiftUI on iOS, a native UI on Android later. | One implementation of every non-UI rule across platforms; links the iSH C kernel directly; the same core runs on macOS for tests and a CLI. |
| 2 | UniFFI with async functions; no synchronous calls across the boundary. | A synchronous boundary let a stuck core freeze the UI, and timeouts only hid it. |
| 3 | Events carry a per-session `seq`; a gap means "fetch a snapshot". | A single recovery path instead of one patch per way an event can be missed. |
| 4 | UI state is a pure reducer over snapshot + events, unit-tested. | Screen state bugs were the most repeated class of defect; they need tests that run without a simulator. |
| 5 | SQLite with one writer thread and numbered migrations. | No blocking on async executors; schema changes that can be tested. |
| 6 | Storage and tool errors propagate; nothing is swallowed. | A message shown but not stored, or a queued message silently dropped, is worse than a visible error. |
| 7 | Device capabilities are individual typed tools. | Measured against the reference app: one call instead of a `--help` round trip, per-capability permission and rendering, and no larger request (Solos's first request was smaller than the reference app's with 23 tools vs 7). Revisit if evals show wrong-tool choices. |
| 8 | Tool descriptions and outputs are evaluated against a real model before and after change. | A single sentence in a description moved the model from opening a page to calling a third-party API; only a measured run showed it. |
| 9 | Behaviour defaults follow the reference app; deviations need a measurement. | Most defects came from deviating without measuring (browser user agent, page-load waiting, fetch framing, weather request shape). |
| 10 | The core emits error kinds, never user-facing prose. | Localisation lives in the app; the core stays language-neutral. |
| 11 | GPL-3.0 with an App Store exception for Solos's own code. | iSH is GPL-3.0 and runs in process; the exception keeps App Store distribution possible, as iSH does. |
| 12 | English for code, comments, commits and developer docs; README also in Simplified Chinese. | Open source contributors. |
| 13 | Thinking is set per session (default from settings) and switched by a request-shaping table; when it is off, thinking parts stay in the transcript but are not drawn. | Some endpoints choose thinking by model id and ignore the switch (measured through an OpenAI-compatible relay: `qwen3.8-max-thinking` reasoned with `enable_thinking` true, false or absent); the reference app hides thinking when off. |
| 14 | The core titles a session after its first reply, using the session's model with thinking off and no tools; if that fails, the first user message, shortened. | One place for a rule every client needs. The request is ~250 characters against the reference app's ~1,200, and the title follows the user's language (the reference app titled a Chinese chat in English). |
| 15 | Retry and edit-and-resend delete the messages after the chosen user message, for real; context management never deletes (it marks). One `Truncated` event tells clients. | The user asked to discard them, and keeping them would send the discarded answer back to the model; the reference app truncates the same way. |
| 16 | Markdown is parsed by swift-markdown (cmark-gfm) and math typeset by SwiftMath; TeX is protected from CommonMark before parsing. | The reference app uses the same two libraries; a hand-written parser was the old prototype's weak point. Both licences (Apache-2.0, MIT) are GPL-3.0 compatible. |
| 17 | The model shows workspace files as `solos://ws/<path>` links; the core maps them to device paths and refuses anything outside the workspace. | One mapping for every client, tested in the core, including `..` and percent-escapes. |
| 18 | Attachments are copied by the core into `/solos/ws/attachments`; photos are sent to it as JPEG with the long edge at most 2000 px; the newest 20 images go to the model as images, other files as an `<attachments>` list of paths and sizes. | The reference app's shapes and limits. Measured with the same photo and question: Solos answered in one request with the image; the reference app did not send the image to this model and needed an OCR tool call and a second request. |
| 19 | Anthropic and Gemini adapters speak raw HTTP; their thinking switches are rows in the shaping table; signed thinking (Anthropic `signature`, `redacted_thinking`, Gemini `thoughtSignature`) is stored on its part with the `protocol:model` that made it and replayed only there. | No official Rust SDK; a signature sent to another model is rejected or ignored. Checked end to end against a local server replaying each API's documented stream format; not yet run against the real services (no key on hand). |
| 20 | Context: the reference app's thresholds by window size; old tool output is cleared in the request only; near the limit the turn stops and asks before summarising; a summary is a mark (undoable) covering all but the last three user turns; a summary request that is itself too long is split in two and chained. Windows come from the endpoint's model list, else unknown. | The reference app summarises without asking; the requirements say ask first, since a summary hides content from the model. Verified with a real model: stopped at 75,769 of 80,000 tokens before sending, summarised, and the continued turn still recalled facts from the summarised part. |
| 21 | The chat's message list is a plain `VStack`; following the stream is a flag only the reader's own scrolling turns off, the ends are read from scroll geometry, and "go to the end" scrolls to the content's bottom edge. The step buttons find the current question from where each question's row starts in the content, against the top of what is on screen; a step stops following the stream. | With replies tens of thousands of characters long, a lazy stack left the chat blank after opening or any change at the bottom — with either scrolling style, measured on screen. Verified on a ~300k-character chat: opens at the newest message, follows a streaming reply, stops following when dragged up (buttons appear, position holds), resumes on "go to the end", and steps between questions. |
| 22 | A running turn holds a background task; a turn that ends while the app is in the background posts "✅/❌ <chat>" with the start of the reply as plain text, and tapping it opens the chat. Permission is asked at the first turn, in the foreground. | The reference app's notification; a background app cannot show the permission prompt. The reference app's optional location/audio keep-alive is not adopted. |

| 25 | Each chat route is distinct (`chat(id)`, `newChat(UUID)`) and the chat view's identity is its route. | Replacing one chat with another at the same place in the stack reused the old view and its state, so "New chat" from inside a chat did nothing (seen on screen). |

| 29 | The terminal is SwiftTerm (MIT, v1.18.0, pinned by commit; later versions add a build plugin every build machine must first trust) over a pty in the guest.
